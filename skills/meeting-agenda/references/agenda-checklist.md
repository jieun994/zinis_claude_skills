# 회의 유형별 아젠다 체크리스트

Step 3에서 이 파일을 읽고, 추론한 회의 유형의 표와 초안을 대조한다.

**이 체크리스트의 역할은 보완이지 본체가 아니다.** 안건의 본체는 언제나 입력 자료(직전 회의록의 미완료 TO-DO, 산출물의 미정 항목, 사용자 메모)에서 나온다. 여기 있는 항목은 그 위에서 "절차상 빠뜨리기 쉬운 것"을 잡는 용도다.

여기서 가져온 항목은 결과물에 `[체크리스트 제안]`으로 표시한다. 표시 없이 자료 근거 항목과 섞으면, 사용자가 "이건 지난 회의에서 나온 얘기구나"라고 잘못 믿게 된다.

가능하면 프로젝트 맥락을 붙여 구체화한다. `다음 마일스톤 확인` 대신 `다음 마일스톤 확인 — 8/20 화면설계 완료 예정일이 유효한지`처럼.

---

## 1. 킥오프 / 초도 미팅

| 기본 확인 안건 | 자주 놓치는 질문 | 결정 필요 신호 |
|---|---|---|
| 프로젝트 목표와 성공 기준 | "이 프로젝트가 실패했다고 판단하는 기준은 뭔가요?" | 목표가 두 개 이상이고 우선순위가 없음 |
| 범위(스코프) — 하는 것과 안 하는 것 | "이번 범위에서 **빠지는** 게 뭔지 서로 확인했나요?" | "일단 넣어두죠" 같은 미확정 범위 |
| 최종 의사결정권자 | "최종 컨펌은 누가 하나요? 오늘 그분이 계신가요?" | 결정권자가 회의에 없음 |
| 커뮤니케이션 채널·주기 | "산출물 검토 기한은 며칠 드리면 되나요?" | 검토 기한 미정 → 일정 리스크 |
| 마일스톤과 오픈 목표일 | "오픈일이 고정인가요, 조정 가능한가요?" | 오픈일 고정 + 범위 미확정 |
| 기존 시스템·자료 제공 일정 | "저희가 받아야 할 자료(계정·디자인·데이터)는 언제 주시나요?" | 제공 일정 미정 |
| 제약 조건(법규·보안·브랜드 가이드) | "지켜야 할 내부 규정이나 심의가 있나요?" | 뒤늦게 발견되면 재작업 |

## 2. 정기 진행 점검

| 기본 확인 안건 | 자주 놓치는 질문 | 결정 필요 신호 |
|---|---|---|
| 지난 회의 TO-DO 완료 여부 | "지난번 미정으로 남긴 항목, 지금 답이 나왔나요?" | 완료일 공란인 TO-DO가 2회 이상 이월됨 |
| 이번 주 진척과 다음 주 계획 | "예정보다 늦어진 항목이 있나요? 만회 계획은?" | 진척률이 계획 대비 벌어짐 |
| 신규 이슈·리스크 | "새로 생긴 걱정거리 있으세요?" | 이슈가 이슈 목록에 안 올라옴 |
| 대기 중인 승인·피드백 | "저희가 기다리고 있는 컨펌이 있어요" | 승인 대기가 일정을 막고 있음 |
| 다음 마일스톤 유효성 | "다음 마일스톤 날짜 그대로 가도 되나요?" | 앞 단계 지연이 뒤로 전이됨 |

## 3. 이슈 해결 / 의사결정

| 기본 확인 안건 | 자주 놓치는 질문 | 결정 필요 신호 |
|---|---|---|
| 이슈의 정확한 현상과 범위 | "이게 어디까지 영향을 주나요?" | 영향 범위가 파악 안 됨 |
| 선택지와 각각의 대가(비용·일정·품질) | "이 안을 고르면 뭘 포기하게 되나요?" | 선택지가 하나뿐 — 비교 대상이 없음 |
| 오늘 결정 안 하면 생기는 일 | "언제까지 결정하면 일정에 지장 없나요?" | 결정 데드라인이 지났거나 임박 |
| 결정 주체와 승인 절차 | "이건 누가 결정해야 하나요?" | 결정권자가 불명확 |
| 결정 후 되돌릴 수 있는지 | "나중에 바꾸면 얼마나 손해인가요?" | 되돌리기 어려운데 정보가 부족 |
| 합의 내용의 기록 방법 | "이 결정 어디에 남길까요?" | 구두 합의만 하고 문서화 안 함 |

## 4. 산출물 검수 / 보고

| 기본 확인 안건 | 자주 놓치는 질문 | 결정 필요 신호 |
|---|---|---|
| 검토 대상 산출물과 버전 | "보고 계신 게 최신 버전 맞나요?" | 상대가 구버전을 보고 있음 |
| 확정할 항목과 보류할 항목 구분 | "오늘 확정되는 건 어디까지인가요?" | 전부 "검토 후 회신"으로 넘어감 |
| 산출물 내 `미정`·`TBD` 항목 | "이 부분 값이 비어 있는데 채워주실 수 있나요?" | 미정 항목이 다음 단계 착수를 막음 |
| 피드백 반영 범위와 추가 요청 구분 | "이건 수정인가요, 추가 요청인가요?" | 범위 밖 요청이 수정으로 위장됨 |
| 컨펌 기한 | "언제까지 확정 회신 주실 수 있나요?" | 기한 없는 "검토해볼게요" |

## 5. 오픈 전 점검

| 기본 확인 안건 | 자주 놓치는 질문 | 결정 필요 신호 |
|---|---|---|
| 미해결 결함(QA 이슈) 목록과 등급 | "오픈을 막는 결함이 몇 개 남았나요?" | 치명 결함이 남은 채 오픈일 임박 |
| 오픈 판단 기준(Go/No-Go) | "어떤 상태면 오픈해도 된다고 보시나요?" | 기준 없이 분위기로 결정 |
| 오픈 당일 역할·연락 체계 | "문제 생기면 누구한테 연락하나요?" | 담당·연락처 미정 |
| 롤백·비상 대응 방안 | "잘못되면 되돌릴 수 있나요?" | 롤백 계획 없음 |
| 오픈 후 운영 인수인계 | "오픈 후 수정 요청은 어떻게 받나요?" | 운영 체계 미정 |
| 콘텐츠·데이터 최종 반영 여부 | "실제 데이터로 바꿔치기 됐나요?" | 테스트 데이터가 남아 있음 |

## 6. 개발 / 디자인 협의

| 기본 확인 안건 | 자주 놓치는 질문 | 결정 필요 신호 |
|---|---|---|
| 구현 가능 여부와 대안 | "이대로 안 되면 가장 가까운 대안은 뭔가요?" | "안 됩니다"만 있고 대안이 없음 |
| 예외·오류 상황 처리 | "이 화면에서 실패하면 사용자에게 뭐가 보이나요?" | 정상 흐름만 정의됨 |
| 데이터 출처와 갱신 주기 | "이 값은 어디서 오고 언제 갱신되나요?" | 출처 미확인 |
| 작업량과 일정 영향 | "이거 하면 며칠 걸리나요? 다른 일정에 영향은?" | 일정 영향 미확인 상태로 확정 |
| 기획 문서와 실제 구현의 차이 | "설계서와 다르게 만들어진 부분 있나요?" | 문서와 구현이 갈라짐 |
| 테스트 방법과 확인 시점 | "저희가 언제부터 확인해볼 수 있나요?" | 확인 시점 미정 |

---

## 유형이 애매할 때

두 유형이 섞인 회의(예: 정기 점검 + 산출물 검수)는 흔하다. 이때는 두 표를 모두 훑되, 회의 목적 한 줄에 더 가까운 쪽을 주로 삼고 다른 쪽에서는 1~2개만 가져온다. 체크리스트 항목이 자료 근거 안건보다 많아지면 무게중심이 잘못된 것이다 — 그럴 땐 항목을 늘리지 말고 "자료를 주시면 구체화된다"고 알린다.
