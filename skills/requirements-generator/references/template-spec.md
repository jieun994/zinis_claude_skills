# 요구사항 정의서 양식 명세 (template-spec)

이 스킬이 만들어내는 엑셀은 실제 SI 프로젝트 산출물인 **`04_요구사항 정의서`** 시트를 그대로 재현한다.

## 1. 시트 구조

- 시트명: `04_요구사항 정의서`
- 1행: 제목 `요구사항 정의서` (병합, 굵게 size 13)
- 2행: 공백
- 3~4행: 헤더 (검정 배경 + 흰색 굵은 글씨). 세로 병합(3:4), 단 `요구사항명`·`요청자`는 하위 컬럼이 있어 가로 병합.
- 5행~: 데이터. 틀고정 `A5`.

## 2. 컬럼 (총 17개 항목 / 21개 열)

| 열 | 헤더 | 하위 | JSON 키 | 설명 |
|----|------|------|---------|------|
| A | No | | (자동) | 순번 1,2,3… |

- 기능: 사용자·관리자가 화면에서 쓰는 동작
- 비기능: 성능·가용성·응답시간 등 수치 요건
- 운영: 배포·백업·모니터링·운영 절차
- 인터페이스: 외부 시스템 연동
- 보안: 인증·암호화·접근통제
- 둘 이상에 걸치면 기능 우선

## 3. 요구사항ID 채번 규칙

**대분류별로 접두어가 다르고, 대분류마다 독립적으로 001부터 채번한다.**

| 대분류 | 접두어 | 예 |
|--------|--------|-----|
| 챗봇 | `REQ-CHT` | REQ-CHT-001 |
| 공통 | `REQ-COM` | REQ-COM-001 |
| 어드민 | `REQ-BOS` | REQ-BOS-001 |
| 시스템 | `REQ-SYS` | REQ-SYS-001 |
| 관리 | `REQ-MNG` | REQ-MNG-001 |
| (그 외) | `REQ-ETC` | REQ-ETC-001 |

스크립트가 자동 처리하므로 JSON에서는 `요구사항ID`를 비워두면 된다. 기존 ID를 수정·이어치기 하는 경우엔 값을 넣으면 스크립트가 번호를 이어서 매긴다.

대분류 체계가 기본 5종과 다른 프로젝트는 입력 JSON 최상위에 선택 키 `prefix_map`(예: `{"주문": "ORD"}`)을 넣으면 기본 맵에 병합된다. 매핑에 없는 대분류는 `ETC`로 채번되고 경고가 출력된다.

## 4. 출처(근거) 컬럼 — 할루시네이션 방지의 핵심

`출처` 컬럼은 **각 요구사항이 어디서 나왔는지**를 반드시 밝히는 자리다.

- 입력 자료에 실제로 있던 요구사항 → 출처에 근거를 적는다.
  - 예: `RFP`, `인텐트통합_V3.1`, `킥오프 회의록 2026-07-06`, `BOS_의견설정_v3.1`
- 입력에 없는데 AI가 관례상 추정해 채운 요구사항 → 출처를 반드시 `AI추정(확인필요)` 로 적는다.
  - 스크립트가 이 행의 출처 셀을 연노랑으로 강조하고, AI추정 비율이 30% 이상이면 경고를 낸다.

**절대 규칙: 출처가 비어 있는 요구사항을 만들지 않는다.** 근거를 못 대면 그건 지어낸 것이다.
(출처가 빈 행이 있으면 스크립트가 해당 출처 셀을 빨간 계열로 강조하고 `출처 누락 N건: REQ-…` 경고를 낸다.)

## 5. 입력 JSON 스키마

```json
{
  "project": "〇〇 프로젝트",
  "requirements": [
    {
      "대분류": "챗봇",
      "중분류": "대화/인텐트",
      "요구사항명_1depth": "배송문의",
      "요구사항명_2depth": "배송기사연결",
      "상세설명": "텍스트 안내형. 기사연결 절차를 RAG로 안내(연결 실행 아님)",
      "유형": "기능",
      "출처": "인텐트통합_V3.1",
      "rfp_id": "SFR-002",
      "q_n": "",
      "요청자_소속": "", "요청자_파트": "", "요청자_이름": "", "요청일시": "",
      "우선순위": "상",
      "난이도": "중",
      "수용여부": "",
      "담당자": "",
      "처리방안": "",
      "관련자료": ""
    }
  ]
}
```

- `대분류`, `요구사항명_1depth`, `상세설명`, `유형`, `출처` 는 사실상 필수.
- 나머지는 모르면 공백으로 둔다. **모르는 값을 지어내 채우지 않는다.**
- `requirements`만 담은 순수 배열 `[ {...}, {...} ]` 로 줘도 동작한다.

## 6. 스크립트 실행

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/build_requirements_xlsx.py" <input.json> <output.xlsx> "프로젝트명"
```

Windows PowerShell: `${CLAUDE_PLUGIN_ROOT}` → `$env:CLAUDE_PLUGIN_ROOT`, `python`이 없으면 `py -3`.

출력(stdout)은 결과 요약 JSON: `count`(생성 건수), `ai_estimated`(AI추정 건수), `ai_ratio_percent`, `warnings`(ID 중복·출처 누락·AI추정 과다 경고).

## 7. 변환 예시 (회의록 원문 → 요구사항 행)

원칙: **한 문장에 기능이 2개면 행을 나눈다 / 같은 기능의 화면·정책 언급은 한 행의 상세설명으로 합친다.**

회의록 원문 (익명 예시 — 예약 시스템):

> "고객이 달력에서 날짜를 골라 예약할 수 있어야 하고, 예약 내역은 마이페이지에서 취소도 가능해야 합니다. 취소는 이용 24시간 전까지만 허용하기로 했습니다. 관리자 쪽에서는 일자별 예약 현황을 엑셀로 내려받을 수 있으면 좋겠습니다."

변환 결과 (3행):

| 대분류 | 중분류 | 요구사항명 1Depth | 요구사항명 2Depth | 상세설명 | 유형 | 출처 |
|--------|--------|------------------|------------------|----------|------|------|
| 공통 | 예약 | 예약 | 예약 등록 | 달력(캘린더)에서 날짜를 선택해 예약을 등록한다 | 기능 | 킥오프 회의록 |
| 공통 | 예약 | 예약 | 예약 취소 | 마이페이지 예약 내역에서 취소 가능. 취소는 이용 24시간 전까지만 허용(정책) | 기능 | 킥오프 회의록 |
| 어드민 | 예약관리 | 예약 현황 | 엑셀 다운로드 | 일자별 예약 현황을 엑셀 파일로 다운로드한다 | 기능 | 킥오프 회의록 |

변환 포인트:
- 첫 문장에 기능이 2개(예약 등록 / 예약 취소) → 행을 나누고, 같은 상위 기능이므로 1Depth(`예약`)는 공유하고 2Depth로 분리한다.
- "취소는 24시간 전까지"는 별도 행이 아니라 예약 취소 행의 상세설명에 정책으로 합친다. (같은 기능의 화면·정책 언급은 한 행)
- 관리자 기능은 대분류를 `어드민`으로 분리해 별도 채번한다.

반례 (잘못된 변환 1건):

| 대분류 | 요구사항명 1Depth | 상세설명 | 유형 | 출처 | 무엇이 잘못됐나 |
|--------|------------------|----------|------|------|----------------|
| 공통 | 예약 기능 | 예약 등록·취소·관리자 엑셀 다운로드 일체 제공 | 기능 | (공백) | 기능 3개를 한 행에 뭉쳐 검증·우선순위·수용여부 판단이 불가능. 출처도 누락 |
